Executive Summary
FixerPro237 is a service platform designed for the Cameroonian market. Its purpose is to simplify technical-service requests while reducing the time clients spend searching for an available technician. The client posts a job instead of manually selecting a technician. FixerPro237 identifies suitable technicians in the same city, prioritizes those with the lowest active-job count, and dispatches the request. Once a technician accepts, the request is assigned to that technician and competing offers are invalidated.
The first version keeps payment outside the platform: the client and technician handle payment directly. FixerPro237 therefore does not integrate MTN Mobile Money or Orange Money at this stage. Live GPS tracking is included for assigned interventions. The implementation uses the same stack selected for the previous project: React, Node.js/Express and Supabase/PostgreSQL.
1. Project Overview
1.1 Purpose
This document defines the functional, technical, data, security, interface, testing and deployment requirements for FixerPro237. It is intended to guide implementation, UML modelling, testing and the final-year academic report.
1.2 Problem Statement
In Cameroon, clients frequently depend on recommendations, WhatsApp groups, social networks and informal contacts to find technicians. This makes availability, reliability and response time difficult to determine. FixerPro237 addresses this problem by centralizing service requests and automating technician dispatch.
1.3 Objectives
Allow authenticated clients to post technical-service requests.
Automatically identify eligible technicians.
Prioritize technicians with fewer active jobs.
Prevent duplicate assignment when several technicians receive an offer.
Allow technicians to manage availability and service status.
Provide technician verification and administrator validation.
Provide live GPS tracking during assigned interventions.
Provide service history, completion and rating/review.
Provide an administration interface.
Remain lightweight enough for common Cameroonian connectivity constraints.

6. Core Business Rules
Only authenticated clients can create service requests.
Only verified and available technicians participate in automatic dispatch.
The technician must match the requested category.
The initial dispatch scope requires the technician and request to be in the same city.
Technicians are ranked by active-job count, lowest first.
A deterministic tie-breaker should be used when active-job counts are equal.
Acceptance must be atomic.
After acceptance, competing offers become invalid.
GPS sharing is available only for an assigned active service.
GPS sharing ends when the service is completed or cancelled.
Payment is not processed by FixerPro237 in V1.
7. Dispatch Algorithm
The defining feature of FixerPro237 is automatic technician dispatch.
dispatch(request):    candidates = technicians where        verified = true        AND available = true        AND category = request.category        AND city = request.city    sort candidates by activeJobCount ASC    for technician in candidates:        create job offer        wait for response        if accepted:            atomically assign request            invalidate all other offers            return ASSIGNED    return UNASSIGNED
For a Year 3 implementation, sequential dispatch is recommended because it is easy to explain and test. The backend must nevertheless perform the final assignment atomically so that simultaneous acceptance cannot produce duplicate ownership.

12. Key Sequence Specifications
12.1 Request Dispatch
Client logs in.
Client submits service request.
React sends the request to the Express API.
API validates and stores the request.
Dispatch service finds verified, available technicians in the same city and category.
Candidates are ordered by active-job count.
System creates an offer for the highest-priority candidate.
Technician accepts or rejects.
On rejection/expiry, the next candidate is considered.
On acceptance, the backend atomically assigns the request.
Other offers are invalidated.
Technician begins service and GPS tracking becomes available.
12.2 GPS Tracking
Technician starts an assigned job.
Location permission is granted.
Technician device sends periodic coordinates.
Backend verifies that the technician owns the request.
Location update is stored.
Authorized client views the latest position and timestamp.
Tracking stops when the service ends.
13. Live GPS Tracking
Only assigned technicians can send GPS updates for a request.
Only the related client and authorized administrators can view the tracking information.
Coordinates include latitude, longitude and timestamp.
Update frequency should balance usefulness, battery consumption and mobile data usage.
When connectivity is interrupted, the client should see the last known position and its timestamp.
Tracking should stop automatically after completion/cancellation.
14. Security
Protected routes require authentication.
Use RBAC for Client, Technician and Administrator permissions.
Validate all request inputs.
Secure verification-document storage and access.
Use HTTPS in deployment.
Use Supabase/PostgreSQL Row Level Security where applicable.
Use rate limiting for authentication and sensitive endpoints.
Protect GPS data through authorization checks.
Use an atomic/conditional database operation for final job assignment.

23. Conclusion
FixerPro237 is a focused evolution of the previous technician-finder concept. The most important change is the service-dispatch model: the client describes the job and FixerPro237 takes responsibility for finding and proposing the job to a suitable technician. This creates a clear technical contribution for the project through eligibility filtering, workload prioritization, offer management and atomic assignment. Live GPS tracking further connects the digital request with the real-world intervention. The project remains appropriate for a Bachelor's Software Engineering implementation because it uses a conventional React + Node.js/Express + Supabase architecture without introducing unnecessary enterprise complexity.
